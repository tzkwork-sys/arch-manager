# Arch Manager — план разработки магазина приложений

**Файл в проекте:** `docs/APP_STORE_PLAN.md`  
**Дата фиксации плана:** 30 сентября 2026  
**Статус:** Этапы 1–4 и промежуточная полировка 3.1 выполнены 30 сентября 2026; Этап 5 выполнен 1 октября 2026; Этап 6 остаётся по плану для отдельного чата.

---

## 1. Цель

Добавить в **Arch Manager** полноценный визуальный раздел **«Приложения»**, который для обычного пользователя выглядит как магазин приложений:

- приложения представлены карточками с иконками;
- есть понятные названия и описания;
- есть категории;
- есть поиск и фильтры;
- у приложения есть отдельная подробная страница;
- видны состояние установки, версия и источник;
- приложение можно установить, удалить и запустить;
- установленными приложениями можно управлять;
- доступные обновления приложений видны в магазине, но выполняются через безопасный общий механизм обновления Arch Linux;
- интерфейс не показывает пользователю тысячи библиотек, служебных пакетов и системных компонентов, если они не являются самостоятельными desktop-приложениями.

Первая версия магазина работает **только с официальными репозиториями Arch Linux**.

AUR в этапы 1–6 **не входит**. Архитектура должна лишь не мешать добавить AUR позднее отдельным циклом разработки.

---

## 2. Основная концепция

Магазин является **частью Arch Manager**, а не отдельным приложением.

Причины:

1. Arch Manager уже умеет работать с обновлениями, привилегированными действиями, точками восстановления и диагностикой.
2. Не нужно создавать второй процесс управления пакетами с отдельной логикой и отдельными правилами безопасности.
3. Общие системные механизмы — обновления, Polkit/helper, уведомления, диагностика — можно использовать повторно.
4. Пользователь получает единый центр управления Arch Linux.

В навигации Arch Manager появляется отдельный самостоятельный раздел:

**Приложения**

Он не должен смешиваться со страницей «Обновления».

---

## 3. Источники данных

### 3.1. Каталог приложений

Основной источник визуальной информации — данные **AppStream**, поставляемые Arch Linux.

Базовый пакет данных:

`archlinux-appstream-data`

Он используется как источник:

- AppStream ID;
- названия;
- краткого и полного описания;
- категорий;
- иконок;
- ссылок на домашнюю страницу;
- лицензии;
- доступных screenshot/media metadata;
- связи desktop-приложения с пакетом Arch.

Мы **не создаём вручную собственную базу описаний** для тысяч программ.

### 3.2. Состояние пакетов

Системная информация берётся из штатной пакетной инфраструктуры Arch:

- установлен / не установлен;
- локальная версия;
- версия в официальном репозитории;
- репозиторий;
- размер;
- зависимости;
- причина установки, где это необходимо;
- наличие обновления.

Нельзя делать парсинг вывода `pacman` частью GUI-слоя. Данные должны проходить через отдельный core/service слой.

### 3.3. Медиа

Иконки в первую очередь берутся из локальных AppStream-данных.

Скриншоты, если AppStream содержит внешние media URL:

- загружаются только асинхронно;
- имеют локальный cache;
- не блокируют открытие страницы;
- при отсутствии сети магазин остаётся работоспособным;
- битая картинка не должна ломать карточку или страницу приложения.

---

## 4. Что считается «приложением»

Магазин показывает **desktop-приложения**, а не весь список пакетов Arch.

В основной каталог не должны автоматически попадать:

- библиотеки;
- `-debug` пакеты;
- заголовочные/devel-компоненты;
- firmware;
- kernel-компоненты;
- command-line зависимости без самостоятельного desktop-приложения;
- служебные runtime-пакеты;
- языковые пакеты;
- плагины, которые сами по себе не являются приложениями;
- метапакеты, если они не должны отображаться пользователю как приложение.

Критерием включения является прежде всего корректный AppStream desktop/application component.

Отдельный технический экран «все пакеты» в рамках этапов 1–6 **не создаём**.

---

## 5. Базовая структура магазина

После завершения всех шести этапов раздел должен иметь следующие пользовательские представления.

### Главная

Блоки:

- рекомендуемые/выделенные категории;
- популярные или заметные приложения — только если появится объективный источник/правило формирования;
- новые приложения — только если данные позволяют определить это корректно;
- недавно установленные — локальная информация;
- переход к полному каталогу.

**Не придумывать рейтинги и оценки**, если у нас нет надёжного источника рейтинга.

### Категории

Пример верхнего уровня:

- Интернет;
- Офис;
- Графика;
- Фото и видео;
- Аудио;
- Разработка;
- Образование;
- Игры;
- Система и инструменты;
- Наука;
- Связь;
- Прочее.

Фактическое отображение категорий строится поверх AppStream categories и нормализуется в небольшой понятный пользователю набор.

### Поиск

Поиск должен учитывать:

1. название приложения;
2. package name;
3. AppStream ID;
4. summary;
5. ключевые слова, если они доступны.

### Установленные

Показываются только приложения из каталога, которые действительно установлены.

### Обновления

Показываются приложения, входящие в текущий набор доступных системных обновлений.

**Важно:** кнопка обновления не должна создавать частичное обновление Arch. Переход выполняется в существующий механизм полного системного обновления Arch Manager.

# ЭТАП 1. Основа магазина: модель данных и read-only каталог

## Цель

Создать надёжное ядро магазина без установки/удаления пакетов и без сложного финального GUI.

Главный результат этапа: Arch Manager умеет локально построить список реальных desktop-приложений из официальных репозиториев и корректно определить их состояние.

## 1.1. Анализ текущей архитектуры Arch Manager

Перед правками:

- проверить актуальное дерево `src/core`, `src/gui`, `tests`;
- определить существующие patterns для фоновых задач;
- определить существующий механизм кеширования;
- определить существующий механизм обновлений;
- определить существующий helper/Polkit architecture;
- не дублировать уже имеющиеся общие классы и функции.

## 1.2. Ввести доменную модель приложения

Минимальная модель `Application` должна уметь хранить:

- `app_id`;
- `package_name`;
- `name`;
- `summary`;
- `description`;
- `categories`;
- `icon`;
- `screenshots`;
- `homepage`;
- `license`;
- `repository`;
- `available_version`;
- `installed_version`;
- `installed`;
- `update_available`;
- `download_size`, если доступен;
- `installed_size`, если доступен;
- desktop entry / launch information;
- признаки корректности/полноты metadata.

Модель не должна зависеть от Qt widgets.

## 1.3. AppStream reader

Реализовать core-компонент, который:

- находит локальные AppStream metadata Arch;
- читает их без root;
- строит список application components;
- связывает AppStream component с package name;
- обрабатывает отсутствующие поля;
- не падает на одном повреждённом/неполном component;
- не блокирует GUI длительным синхронным parsing.

## 1.4. Package-state provider

Реализовать read-only слой, который определяет:

- установлен ли пакет;
- локальную версию;
- доступную версию;
- репозиторий;
- размер;
- есть ли обновление.

Никаких системных изменений этот слой не делает.

## 1.5. Объединение AppStream + package state

Создать единый `AppCatalogService`.

Задачи:

- AppStream отвечает за «человеческое» представление;
- пакетный слой отвечает за состояние системы;
- GUI получает готовые `Application` objects;
- GUI не запускает `pacman` напрямую.

## 1.6. Cache

На первом этапе создать cache для уже разобранного каталога.

Cache должен инвалидироваться при изменении как минимум:

- AppStream metadata;
- package database state;
- версии/формата cache самого Arch Manager.

Хранить cache в пользовательском cache-каталоге, а не внутри исходников проекта.

## 1.7. Минимальный диагностический вывод

До полноценного GUI должен существовать способ проверить каталог тестом/core-вызовом:

- сколько AppStream components найдено;
- сколько преобразовано в приложения;
- сколько связано с официальными пакетами;
- сколько установлено;
- примеры нескольких записей.

Это нужно для ранней проверки качества данных.

## 1.8. Тесты этапа 1

Покрыть:

- parsing AppStream;
- пропущенные поля;
- связь component → package;
- installed / not installed;
- version mapping;
- category normalization;
- invalid metadata;
- cache invalidation;
- отсутствие AppStream data;
- пустой каталог;
- duplicate components/package mappings.

### Реализация этапа 1

Реализовано отдельным feature-пакетом `src/app_store/`, без подключения к Qt-навигации и без привилегированных действий:

- `models.py` — доменная модель `Application`;
- `appstream.py` — read-only чтение системного AppStream-каталога Arch;
- `package_state.py` — read-only состояние официальных пакетов через pacman;
- `catalog.py` — объединение AppStream + package state и асинхронный API;
- `cache.py` — пользовательский cache с инвалидированием по AppStream и pacman DB;
- `categories.py` — нормализация категорий;
- `diagnostics.py` — диагностический core/CLI-вывод;
- `tests/test_app_store_stage1.py` — регрессионные тесты этапа.

GUI-раздел «Приложения» намеренно не подключён: это задача Этапа 2.

## Критерий готовности этапа 1

Этап завершён, если:

- ядро получает каталог официальных desktop-приложений;
- библиотеки и обычные системные пакеты не засоряют результат;
- состояние установки определяется правильно;
- GUI пока ничего не устанавливает;
- тесты проекта проходят;
- новая логика не ломает существующие страницы Arch Manager.

# ЭТАП 2. Главный интерфейс каталога

**Статус этапа 2:** выполнен 30 сентября 2026.

## Цель

Сделать полноценную страницу «Приложения» для просмотра каталога.

На этом этапе магазин всё ещё read-only: никаких установок и удалений.

## 2.1. Навигация

Добавить пункт:

**Приложения**

в существующую навигацию Arch Manager.

Порядок разделов определить по текущему интерфейсу на момент реализации, не перестраивая весь Arch Manager ради магазина.

## 2.2. Макет

Основные зоны:

- заголовок «Приложения»;
- строка поиска;
- категории/фильтры;
- область карточек;
- переключение на «Установленные»;
- состояния загрузки/пустого результата/ошибки.

## 2.3. Карточка приложения

Карточка содержит:

- иконку;
- название;
- короткое описание;
- категорию или компактный маркер;
- состояние «Установлено», если применимо.

Карточка не должна быть перегружена:

- package name;
- зависимости;
- размер;
- лицензия;
- repository

показываются на подробной странице, а не постоянно в каталоге.

## 2.4. Адаптивная сетка

При изменении размера окна:

- число колонок меняется автоматически;
- карточки не становятся чрезмерно широкими;
- не появляется горизонтальная прокрутка;
- вертикальное пространство используется полностью.

## 2.5. Поиск

Требования:

- поиск без кнопки «искать»;
- debounce, чтобы не фильтровать тяжёлый каталог на каждый мгновенный event;
- результаты обновляются быстро;
- search не блокирует GUI;
- очистка строки немедленно возвращает каталог.

## 2.6. Категории и фильтры

Минимум:

- Все;
- категории;
- Установленные.

Дополнительные фильтры можно добавить, если они действительно полезны:

- только GUI;
- repository;
- наличие screenshot.

Не добавлять фильтры ради количества.

## 2.7. Виртуализация/ленивая загрузка

Нельзя создавать тысячи тяжёлых Qt widgets одновременно.

Реализация должна обеспечивать:

- lazy creation;
- pagination или virtualized/grid batching;
- ленивую загрузку иконок;
- отсутствие заметных подвисаний при прокрутке.

## 2.8. Тесты этапа 2

Проверить:

- страница открывается;
- поиск;
- категории;
- фильтр установленных;
- пустой результат;
- ошибка загрузки metadata;
- resizing;
- повторное открытие страницы;
- cache;
- большое число приложений.

## Критерий готовности этапа 2

Пользователь может открыть Arch Manager → «Приложения», быстро просматривать официальный каталог, искать приложения и фильтровать их по категориям.

Система пока ничего не изменяет.

# ЭТАП 3. Подробная страница приложения и медиа

## Цель

Сделать карточку приложения информативной настолько, чтобы пользователь мог принять решение об установке.

## 3.1. Экран приложения

По нажатию на карточку открывается подробная страница или большой dialog/page, соответствующий стилю Arch Manager.

Содержимое:

- крупная иконка;
- название;
- summary;
- полное описание;
- скриншоты;
- версия;
- repository;
- размер;
- лицензия;
- homepage;
- package name;
- состояние установки;
- информация об обновлении;
- кнопка действия, пока отключённая/read-only на этом этапе.

## 3.2. Скриншоты

Требования:

- горизонтальная галерея;
- первый screenshot может использоваться как preview;
- загрузка только для открытой страницы;
- memory/disk cache;
- placeholder;
- retry;
- timeout;
- битый URL не ломает страницу.

## 3.3. HTML/markup descriptions

AppStream descriptions могут содержать markup.

Нужно:

- безопасно преобразовывать поддерживаемую разметку;
- не исполнять произвольный HTML/JS;
- корректно показывать списки и абзацы;
- иметь plain-text fallback.

## 3.4. Ссылки

Внешние ссылки:

- homepage;
- bug tracker / help — только если metadata содержит их и это уместно.

Открываются стандартным механизмом рабочего стола.

## 3.5. Отсутствующие данные

Если нет:

- screenshot;
- icon;
- description;
- license;
- homepage

страница должна аккуратно скрывать отсутствующий блок, а не показывать пустые рамки.

## 3.6. Тесты этапа 3

Покрыть:

- полная metadata;
- минимальная metadata;
- отсутствующая иконка;
- отсутствующие screenshots;
- network failure;
- malformed description;
- повторное открытие;
- cache media;
- очень длинные description/name.

## Критерий готовности этапа 3

Каталог выглядит как настоящий software center: пользователь может открыть приложение и увидеть понятное описание, иконку, основные технические сведения и доступные изображения.

**Статус этапа 3:** выполнен 30 сентября 2026. Реализована read-only подробная страница, безопасная AppStream-разметка, внешние ссылки и ленивый media-cache скриншотов с placeholder/retry/timeout.

## Промежуточный этап 3.1 — полировка подробной страницы

После визуальной проверки этапа 3 добавлена UX-полировка перед подключением пакетных действий:

- обычное колёсико мыши над галереей прокручивает скриншоты горизонтально;
- полоса горизонтальной прокрутки скрыта, при реальном переполнении доступны компактные стрелки;
- загруженный скриншот открывается по клику в крупном просмотрщике;
- просмотрщик поддерживает максимизированный режим, полноэкранный режим, клавиши ←/→, F11 и Esc;
- описание больше не имеет собственной вертикальной прокрутки и автоматически занимает высоту по содержимому;
- короткое описание не создаёт большой пустой прямоугольник;
- у установленного приложения read-only кнопка действия подписана «Удалить», у неустановленного — «Установить»; фактическое действие по-прежнему подключается только на этапе 4.

**Статус этапа 3.1:** выполнен 30 сентября 2026.

# ЭТАП 4. Безопасная установка, удаление и запуск

**Статус реализации:** выполнен 30 сентября 2026. Добавлены отдельный package-action contract, read-only preview через pacman, whitelist root-helper `manage-applications`, Polkit policy/installer, защита от частичных обновлений, установка/удаление, запуск desktop-приложений от пользователя, busy-state и обработка ошибок.

## Цель

Превратить read-only каталог в рабочий магазин.

Это первый этап, где Arch Manager изменяет систему.

## 4.1. Разделить GUI и привилегированные действия

GUI не получает root.

Схема:

`GUI → action contract → privileged helper → package manager`

Использовать тот же общий подход, который уже принят в Arch Manager для привилегированных системных действий.

## 4.2. Разрешённые действия helper

Минимальный whitelist:

- install one selected official application/package;
- remove one selected installed application/package;
- получить machine-readable progress/status, если это реализуемо безопасно.

Helper не должен превращаться в «выполнить любую строку shell от root».

## 4.3. Проверка входных данных

Перед системным вызовом:

- package name обязан существовать в официальной sync database;
- package name передаётся как аргумент, не shell string;
- запрещены произвольные flags от GUI;
- нельзя подменить repository;
- нельзя передать shell operators/path.

## 4.4. Правило Arch Linux: никаких частичных обновлений

Магазин не должен выполнять опасную последовательность:

`pacman -Sy <package>`

Если для установки требуется синхронизация package databases, операция должна быть согласована с поддерживаемым полным обновлением системы.

Практический принцип:

- не обновлять sync DB отдельно от system upgrade;
- использовать существующую актуальную package state, когда это безопасно;
- если состояние требует полного обновления — сначала направлять операцию через существующий Update flow Arch Manager;
- после полного обновления продолжать/повторять установку.

## 4.5. Установка

UX:

1. пользователь нажимает «Установить»;
2. Arch Manager показывает короткое подтверждение, если операция затронет дополнительные пакеты;
3. начинается операция;
4. карточка показывает progress/state;
5. после успеха состояние меняется на «Установлено»;
6. появляется «Запустить», если desktop entry доступен.

Не нужно выводить сырой terminal log как основной UX.

Для ошибок должна быть доступна кнопка/область «Подробности».

## 4.6. Удаление

До удаления показать:

- имя приложения;
- основной package;
- какие зависимости/пакеты будут удалены по выбранной безопасной политике.

Не использовать разрушительные pacman flags, отключающие dependency checks.

Не удалять пользовательские настройки из `$HOME` автоматически.

## 4.7. Запуск

Запуск desktop-приложения:

- выполняется от пользователя;
- не через root helper;
- предпочтительно через desktop entry/application launcher semantics;
- не строится из непроверенной shell-строки.

## 4.8. Busy state

Одновременно не должны стартовать конфликтующие package transactions.

Если уже идёт:

- системное обновление;
- установка;
- удаление;
- другая pacman transaction

магазин должен корректно ждать/блокировать новое действие и объяснять причину.

## 4.9. Ошибки

Понятные состояния:

- нет сети;
- package database недоступна;
- pacman lock занят;
- недостаточно места;
- конфликт пакетов;
- ошибка подписи;
- mirror error;
- пользователь отменил авторизацию;
- helper отсутствует/устарел.

## 4.10. Тесты этапа 4

Обязательно:

- helper whitelist;
- invalid package names;
- argument injection;
- install success/failure;
- remove success/failure;
- concurrent transaction protection;
- Polkit cancel;
- GUI state after failure;
- state refresh after success;
- отсутствие `pacman -Sy package`;
- запуск приложения без root.

Реальные системные операции в тестах должны быть изолированы/mocked там, где тест не предназначен для интеграционной машины.

## Критерий готовности этапа 4

Из Arch Manager можно безопасно установить официальное приложение, удалить его и запустить, не выдавая GUI root и не нарушая базовые правила обновления Arch Linux.

# ЭТАП 5. Установленные приложения и интеграция с обновлениями Arch Manager

**Статус: выполнен 1 октября 2026.**

## Цель

Связать магазин с уже существующими возможностями Arch Manager, чтобы не появились два независимых центра обновлений.

## 5.1. Раздел «Установленные»

Отображает:

- установленные приложения из AppStream-каталога;
- версии;
- доступные обновления;
- запуск;
- удаление;
- переход на подробную страницу.

Не смешивать сюда все installed packages.

## 5.2. Раздел «Обновления приложений»

Задача раздела — **показать**, какие desktop-приложения затрагиваются общим системным обновлением.

Он может показывать, например:

- Firefox `X → Y`;
- VLC `X → Y`;
- KWrite `X → Y`.

Но кнопка:

**Обновить**

должна запускать/открывать существующий безопасный **полный System Update flow** Arch Manager.

Не создавать отдельное «обновить только Firefox».

## 5.3. Единый источник update state

Страница «Обновления» Arch Manager и магазин не должны независимо запускать разные проверки и получать противоречивые результаты.

Нужно выделить/переиспользовать единый update state/service.

## 5.4. Обновление состояний между страницами

После:

- установки;
- удаления;
- полного обновления системы

состояния должны синхронно обновляться в:

- магазине;
- «Установленных»;
- «Обновлениях»;
- Overview, если там есть соответствующие counters.

Без необходимости перезапускать Arch Manager.

## 5.5. История/последнее действие

Достаточно компактного локального состояния:

- что установлено/удалено через Arch Manager;
- время последней операции;
- результат.

Не строить сложную telemetry/analytics систему.

## 5.6. Restore point policy

Для **полного системного обновления** продолжает работать существующий механизм защитной точки восстановления Arch Manager.

Для обычной установки одного приложения отдельная snapshot-policy определяется на этапе реализации после анализа текущего Recovery/restore-point contract.

Критерий: магазин не должен создавать десятки бессмысленных snapshots при каждой мелкой операции.

## 5.7. Тесты этапа 5

Покрыть:

- install → Installed page update;
- remove → исчезновение из Installed;
- system update availability;
- mapping package update → application;
- несколько AppStream components на один package;
- один component с несколькими связанными package metadata;
- общий update state;
- отсутствие partial upgrade path;
- переход к существующей странице обновлений.

## Критерий готовности этапа 5

Магазин ощущается частью Arch Manager: установка, список установленных приложений и системные обновления используют согласованные данные и не конфликтуют друг с другом.

# ЭТАП 6. Доводка до стабильного релиза

> Статус: **выполнено 01.10.2026**. Реализация зафиксирована в `docs/APP_STORE_STAGE6.md`.

## Цель

Сделать магазин пригодным для постоянного ежедневного использования и подготовить архитектуру к будущему расширению.

## 6.1. Производительность

Цели:

- первый показ страницы без длительного «белого окна»;
- parsing и package queries вне GUI thread;
- disk cache;
- lazy icons;
- lazy screenshots;
- ограничение параллельных network requests;
- отсутствие повторного parsing при каждом переходе на страницу;
- memory cache с разумными пределами.

## 6.2. Offline mode

Без сети пользователь всё равно должен видеть:

- локальный каталог;
- установленные приложения;
- сохранённые иконки;
- ранее закешированные screenshots.

Сетевые функции просто получают понятное состояние «нет подключения».

## 6.3. Обновление AppStream metadata

Нельзя вводить собственный параллельный updater.

AppStream data обновляется штатным package manager вместе с системой.

После изменения metadata Arch Manager автоматически инвалидирует свой cache.

## 6.4. Внешний вид

Финальная унификация с Arch Manager:

- размеры отступов;
- typography;
- кнопки;
- badges;
- hover;
- dialogs;
- progress;
- error states;
- dark/light Plasma themes;
- HiDPI;
- длинные русские/английские названия.

## 6.5. Доступность

Проверить:

- keyboard navigation;
- focus;
- tab order;
- readable labels;
- tooltips только там, где нужны;
- отсутствие действий, доступных исключительно через hover.

## 6.6. Надёжность cache

Cache:

- versioned;
- atomic write;
- не ломает приложение при повреждении;
- может быть полностью пересоздан;
- имеет ограничение по размеру для media;
- очищается по LRU/возрасту или аналогичному понятному правилу.

## 6.7. Packaging/dependencies

Зафиксировать необходимые зависимости Arch Manager.

Новые обязательные зависимости не должны устанавливаться «молча».

При отсутствии AppStream data:

- страница показывает понятное объяснение;
- предлагается штатный безопасный способ установить требуемый официальный пакет;
- остальной Arch Manager продолжает работать.

## 6.8. Финальный тестовый контур

Обязательные классы тестов:

### Unit

- models;
- parsing;
- filtering;
- category mapping;
- cache;
- package-state mapping.

### GUI

- page load;
- search;
- categories;
- details;
- install/remove states;
- errors;
- resizing.

### Security

- helper;
- Polkit action;
- invalid inputs;

### Integration

- local AppStream data;

### Regression

Полный существующий `pytest` Arch Manager должен проходить.

## 6.9. Документация

Обновить:

## 6.10. Финальная приёмка

Перед объявлением магазина завершённым вручную проверить сценарии:

1. открыть магазин сразу после запуска Arch Manager;
2. найти Firefox/KWrite/VLC или другое реально доступное приложение;
3. открыть подробности;

6. убедиться, что приложение отображается установленным;
7. запустить его;
8. удалить приложение;
9. проверить поведение без сети;
10. проверить большой каталог и прокрутку;
11. проверить full system update;
12. проверить, что Recovery/Restore Points/Service/Diagnostics не получили регрессий.

Магазин:

# 6. Архитектурные границы, которые нельзя нарушать

## 6.1. GUI не управляет pacman напрямую

Никаких:

- `sudo` из Qt widgets;
- shell command assembly из строк интерфейса;
- произвольных root commands.

## 6.2. Read-only и write operations разделены

Чтение каталога, поиск и просмотр не требуют root.

Root используется только в минимальном helper для конкретных разрешённых операций.

## 6.3. Один пакетный transaction manager

Магазин и страница обновлений не должны параллельно конкурировать за pacman.

## 6.4. Никакого `pacman -Sy package`

Arch Manager не должен создавать неподдерживаемое partial-upgrade состояние.

## 6.5. Не превращать магазин в Synaptic

Цель — каталог **приложений**, а не фронтенд ко всем 15+ тысячам технических пакетов.

## 6.6. Не хранить собственную копию базы Arch в проекте

Каталог строится из актуальных системных metadata.

## 6.7. Не смешивать AUR с official repos незаметно

Когда AUR появится позже, источник должен быть явно виден пользователю.

# 10. Правила работы по отдельным чатам

Каждый этап выполняется в отдельном чате.

Название/смысл:

- **Этап 1 — ядро каталога**
- **Этап 2 — интерфейс каталога**
- **Этап 3 — страница приложения**
- **Этап 4 — установка и удаление**
- **Этап 5 — установленные и обновления**
- **Этап 6 — стабилизация и релиз**

В начале каждого нового чата:

1. пользователь прикладывает свежий архив Arch Manager;
2. указывает номер этапа;
3. работа ведётся только в границах этого этапа;
4. перед изменениями анализируется актуальный код;
5. изменения передаются одним логически законченным Bash-скриптом;
6. скрипт делает резервную копию изменяемых файлов;
7. после применения запускаются syntax checks и `pytest`;
8. только после успешной проверки этап считается завершённым;
9. в `docs/APP_STORE_PLAN.md` можно отметить выполненный этап и фактические архитектурные решения.

Не начинать следующий этап, пока текущий не доведён до рабочего состояния.

# 12. Итоговая формулировка продукта

После шести этапов Arch Manager должен давать пользователю ощущение обычного современного магазина приложений, но оставаться корректным для философии и технической модели Arch Linux:

**визуальный каталог приложений сверху — штатная пакетная инфраструктура Arch снизу.**

Пользователю не нужно знать package name, разбираться в зависимостях или листать тысячи служебных пакетов, чтобы найти и установить обычную desktop-программу.

При этом Arch Manager не скрывает источник пакета, не подменяет pacman собственной пакетной системой и не нарушает правила безопасного обновления rolling-release системы.

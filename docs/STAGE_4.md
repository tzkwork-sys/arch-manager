# Этап 4 — действия с точками восстановления

Статус: **завершён в 0.4.4-stage4**.

## Граница этапа

Этап 4 добавляет управление точками восстановления и их безопасной автоматизацией:

- создание;
- переименование;
- изменение отметки «Важная»;
- удаление;
- создание важных точек перед будущими обновлениями Arch Manager;
- автоматические точки по времени;
- рекомендуемую политику хранения и автоочистку.

**Восстановление системы в этап 4 не входит.** Оно остаётся отдельным более поздним этапом.

## Шаг 4.1 — контракт действий и валидация

На первом шаге добавлен UI-независимый контракт четырёх разрешённых действий в
`src/core/restore_point_actions.py`.

Он:

- принимает только положительные ID существующих точек;
- приводит пользовательское название к одной строке;
- отклоняет пустые, управляющие и чрезмерно длинные названия;
- принимает важность только как логическое значение;
- формирует фиксированный набор аргументов для будущего privileged helper.

На шаге 4.1 **нет выполнения команд Snapper, sudo или pkexec**. GUI также пока не
получает кнопки изменения данных. Это намеренная граница безопасности перед
подключением привилегированного helper-компонента.

## Шаг 4.2 — минимальный privileged helper

Добавлен `src/privileged/manage_restore_points.sh`. Это пока только исходный
helper внутри проекта: он **не установлен** в систему и GUI его не вызывает.

Helper:

- принимает только `create`, `rename`, `set-importance`, `delete`;
- повторно валидирует ID, важность и описание на привилегированной стороне;
- использует фиксированный `/usr/bin/snapper`;
- для реальных операций требует root;
- не содержит `eval`, `sudo`, `pkexec`, `bash -c` или произвольного запуска команд;
- создаёт только single-точки с cleanup-алгоритмом `number`;
- при изменении важности читает существующие userdata через JSON и сохраняет
  остальные ключи, меняя только `important`;
- выдаёт короткий стабильный результат `OK` для будущего слоя GUI.

`--self-test` проверяет только внутреннюю валидацию и не обращается к Snapper.

## Шаг 4.3 — системная установка helper и Polkit

Добавлена отдельная установка privileged helper без запуска GUI от root.

Системная интеграция использует:

- `/usr/local/libexec/arch-manager/manage-restore-points` — root-owned helper `0755`;
- `/usr/share/polkit-1/actions/org.archmanager.manage-restore-points.policy` — отдельное Polkit-действие, привязанное к точному пути helper;
- `/etc/polkit-1/rules.d/00-arch-manager-restore-points.rules` — локальное правило только для пользователя, запустившего установку из активной локальной сессии.

Правило дополнительно проверяет точный путь программы и то, что `pkexec`
запрашивает запуск helper именно от `root`. Для каждого будущего действия
используется `AUTH_ADMIN`, а не `AUTH_ADMIN_KEEP`: права не кешируются между
операциями. `NOPASSWD`, sudoers и запуск произвольных команд не используются.

Установка выполняет только `--self-test` helper и регистрацию Polkit-действия.
Создание, изменение и удаление реальных точек восстановления на этом шаге не
выполняются. Для отката добавлен `scripts/uninstall-stage4-helper.sh`.

> Совместимость Polkit: action-файл устанавливается в канонический `/usr/share/polkit-1/actions`, потому что именно этот каталог фактически регистрируется через `pkaction` на целевой системе.

## Шаг 4.4 — Python-исполнитель через Polkit

Добавлен `src/core/restore_point_executor.py` — единственная Python-граница Stage 4
для запуска изменяющих операций с повышением прав.

Исполнитель:

- принимает только `RestorePointActionRequest` и повторно валидирует его перед запуском;
- использует фиксированные `/usr/bin/pkexec` и установленный root-owned helper;
- не запускает shell, `sudo`, произвольные программы или пользовательские пути;
- перед запуском проверяет, что helper — обычный файл `root:root`, не является symlink
  и недоступен на запись группе/остальным;
- различает отмену окна Polkit (код 126), отказ/ошибку авторизации (127), ошибку
  helper и timeout;
- строго проверяет машинно-читаемый ответ helper и не принимает неожиданный вывод.

GUI на шаге 4.4 исполнитель **ещё не вызывает**, поэтому запуск приложения и экран
точек восстановления остаются без новых изменяющих кнопок. Тесты подменяют
`subprocess.run`; реальный `pkexec` и Snapper в тестах не запускаются.

## Шаг 4.5 — создание точки из GUI

Экран точек восстановления впервые подключён к изменяющей операции Stage 4.
Добавлены отдельный диалог и фоновый worker для создания новой точки.

Пользователь задаёт название и при необходимости отмечает точку как важную.
После подтверждения GUI передаёт только валидированный `RestorePointActionRequest`
в Python-исполнитель шага 4.4. GUI не запускает `pkexec`, Snapper или shell-команды
напрямую. Системное окно Polkit появляется только после нажатия «Создать».

На время операции кнопка создания блокируется. Отмена авторизации обрабатывается
отдельно от ошибок helper/Snapper. После успешного создания список перечитывается,
а новая точка становится текущей, если она видима с активными фильтрами.

Поскольку это первая реальная изменяющая операция GUI, версия повышена до
`0.4.0-stage4`. Переименование, изменение важности и удаление на шаге 4.5 ещё
не подключены.

## Шаг 4.6 — полировка создания и визуальная нумерация

После первого GUI-действия был улучшен UX экрана точек восстановления. Кнопка
создания перенесена в общий верхний toolbar рядом с обновлением списка, чтобы
она выглядела частью основного рабочего потока, а не отдельной кнопкой сбоку.

Поскольку Snapper не предоставляет точный процент выполнения создания
single-точки, экран не показывает ложный прогресс 0–100 по времени. Вместо
этого добавлена отдельная карточка хода операции с честными этапами:
подготовка запроса, ожидание подтверждения администратора и выполнения
Snapper, затем обновление списка в интерфейсе. Это даёт пользователю понятную
обратную связь без блокирующего информационного popup после успеха.

Также изменена нумерация в списке. UI теперь показывает отдельную визуальную
нумерацию `№`, которая пересчитывается по текущему списку после удаления,
сортировки и фильтрации. При этом технический идентификатор Snapper не
изменяется и остаётся доступен в деталях как `Snapper ID`, поскольку это
системный идентификатор и его нельзя безопасно перенумеровывать ради
интерфейса.

## Шаг 4.7 — меню действий и переименование

В каждой строке списка добавлено компактное меню `⋯`. На этом шаге в нём
доступно только действие «Переименовать» — изменение важности и удаление
специально не смешиваются с первым row-action.

Переименование использует отдельный диалог, существующий валидированный
`build_rename_request` и тот же Python executor/Polkit helper, что и создание.
Во время операции используется уже существующая карточка прогресса, а после
успеха список перечитывается и переименованная точка остаётся выбранной.
Технический `Snapper ID` не меняется.

Одновременно убран символ `＋` из текста кнопки создания, который в некоторых
темах отображался как пустой квадрат. Теперь используется обычный текст
«Создать точку» и системная theme-icon `list-add`, если она доступна.

## Шаг 4.8 — завершение меню управления точкой

После успешной проверки переименования следующий шаг укрупнён: в один логически
завершённый блок объединены изменение важности, удаление и связанные UX-доработки.

Меню `⋯` теперь содержит:

- «Переименовать»;
- «Пометить как важную» / «Убрать из важных» в зависимости от текущего состояния;
- отделённое destructive-действие «Удалить…».

Изменение важности проходит через существующий `build_set_importance_request` и
privileged helper. Helper сохраняет остальные Snapper userdata, поэтому смена
флага `important` не стирает служебные поля точки. После успеха список и счётчик
важных точек перечитываются.

Удаление проходит через отдельный подтверждающий диалог: пользователь видит имя,
дату, статус и технический Snapper ID, а также явное предупреждение, что операция
не отменяется из Arch Manager. Только после этого запускаются валидированный
`build_delete_request`, executor и Polkit. После удаления список перечитывается,
визуальная нумерация пересчитывается, а GUI выбирает соседнюю строку.

Дополнительно исправлено пустое состояние: если удалена последняя точка, на
экране остаётся доступна кнопка «Создать точку», поэтому пользователь не попадает
в тупик.

На шаге 4.8 CRUD-управление отдельными точками завершено: создание,
переименование, важность и удаление подключены к GUI. Политика автоматического
создания точек остаётся отдельным более крупным блоком Stage 4.

## Шаг 4.9 — автоматизация и политика хранения

Финальный крупный блок Stage 4 переносит настройки автоматических точек из legacy
в новый backend и GUI. В разделе «Настройки» теперь доступны три связанные части:

- постоянная пользовательская настройка «создавать важную точку перед обновлением»;
- включение/выключение точек по времени через стандартный `snapper-timeline.timer`;
- применение рекомендуемой политики хранения Arch Manager.

Настройка защиты перед обновлением сохраняется в `QSettings` под стабильным ключом
`restorePoints/createBeforeUpdates`. На Stage 5 экран обновлений будет читать этот
ключ перед установкой и, если защита включена, создавать важную точку через уже
готовый Stage 4 executor. Сам Stage 4 обновления пока не устанавливает.

Для системной политики добавлены отдельные `restore_point_policy*.py`: read-only
backend состояния, валидированный контракт двух разрешённых policy-действий и
исполнитель через уже существующий root-owned helper/Polkit. GUI не запускает
Snapper или systemd напрямую.

Read-only helper получил фиксированный режим `--policy`: он возвращает только
известные параметры конфигурации root и состояния таймеров. Изменяющий helper
получил только два новых фиксированных действия: `policy-apply-recommended` и
`timeline-set yes|no`. Произвольные ключи Snapper, unit-имена и команды из GUI
не принимаются.

Рекомендуемая политика задаёт до 10 обычных и 5 важных точек, включает number-
cleanup, служебный `snapper-cleanup.timer` и лимиты timeline 5/7/4/3/0. В отличие
от legacy-меню, применение политики хранения **не переключает** пользовательский
режим timeline: включение/выключение автоматических точек остаётся отдельным
явным действием. Существующие точки при применении политики немедленно не
удаляются — дальнейшую очистку выполняет Snapper по своим правилам.

Настройки читаются и меняются в фоновых workers. Для изменения системных
параметров появляется стандартное подтверждение Polkit; отмена авторизации
обрабатывается отдельно от ошибок Snapper/systemd.

## Итог Stage 4

Stage 4 завершён. Новый GUI полностью управляет жизненным циклом отдельной точки
и основными правилами её автоматического создания/хранения. Восстановление
системы намеренно не входит в этот этап.

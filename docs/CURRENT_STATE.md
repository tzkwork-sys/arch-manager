## Новая модель Stage 7 Recovery

Recovery-среда теперь общая и не привязана к snapshot.

В обычном Arch:

- при первом открытии страницы «Восстановление» readiness проверяется полностью;
- при повторном входе используется быстрый fingerprint, а полная проверка повторяется только после изменения состояния или вручную;
- отсутствующая или устаревшая среда автоматически подготавливается;
- отдельного выбора snapshot и отдельной кнопки подготовки больше нет;
- после готовности активна только основная кнопка «Перезагрузить в режим восстановления»;
- новые точки восстановления не требуют переподготовки среды.

После перезагрузки:

- Recovery mode сам читает текущий `@snapshots`;
- пользователь выбирает точку уже на автономном чёрном экране;
- видимая нумерация точек всегда компактная `1…N`, независимо от пропусков реальных Snapper ID;
- после выбора точки восстановление начинается автоматически, без повторного подтверждения;
- во время транзакции показываются только короткие текстовые этапы без процентных progress-bar;
- после успешного восстановления остаётся один финальный запрос: любая клавиша — перезагрузка, `0` — выход без перезагрузки;
- `0` на экране выбора точки по-прежнему отменяет восстановление и в local/USB mode возвращает в обычный Arch.

`prepared_snapshot_id` удалён из readiness/state model. Read-only state helper v2 использует `environment_ready`, `iso_ready`, `boot_files_ready` и быстрый `fingerprint`. Авторитетная полная проверка по-прежнему определяется по trusted profile/engine metadata и SHA-256; fingerprint нужен только для дешёвого обнаружения изменений между переходами по вкладкам.

## Интерфейс Recovery

«Точки восстановления» и «Восстановление» объединены в одну страницу **«Восстановление»**:

- сверху — компактная таблица snapshots с созданием, меню строки и пакетным удалением выделенных строк;
- поиск, счётчики, размер snapshots и постоянные служебные подписи убраны;
- несколько строк выбираются стандартно через `Ctrl`/`Shift`, затем удаляются одной командой после общего подтверждения;
- ниже — единый блок **«Способ восстановления»** с двумя переключаемыми вариантами: **«Локальное восстановление»** и **«Аварийная USB-флешка»**;
- показывается только панель выбранного способа: для local — готовность и one-shot reboot, для USB — выбор физического накопителя, создание/обновление и загрузка с флешки.

Первичная загрузка списка ускорена за счёт отказа от дорогостоящего `btrfs filesystem du` для каждого snapshot. Последующие открытия используют локальный cache, валидируемый дешёвым fingerprint metadata Snapper. Recovery readiness также кэшируется между запусками GUI и повторно выполняет тяжёлую SHA-256 проверку только при изменении ISO/profile/engine/boot-файлов. Изменение состава snapshots само по себе больше не инвалидирует общую Recovery-среду.

Recovery boot использует `quiet loglevel=3`, отключённый вывод статусов systemd/udev и сохраняет диагностические сообщения в journal/dmesg, чтобы предупреждения ненужного в Recovery аудиостека SOF не рисовались поверх TTY-мастера.


## USB Recovery

USB использует не отдельную копию логики восстановления, а тот же `recovery/archiso` и тот же `arch-recovery.sh`, что и локальный режим. Различается только путь загрузки.

Создание флешки:

- GUI показывает только whole-disk USB/removable устройства и исключает диск, на котором работает текущий `/`;
- перед записью пользователь видит отдельное подтверждение, что данные будут уничтожены;
- root-owned helper повторно валидирует выбранный диск, размонтирует его разделы, записывает актуальный ISO целиком и сверяет записанные байты по SHA-256;
- ISO имеет метку `AM_RECOVERY`, поэтому GUI различает обычную флешку и уже созданный Recovery-носитель.

Одноразовая загрузка с USB:

- доступна при UEFI и установленном `/usr/bin/efibootmgr`;
- helper сначала сверяет содержимое флешки с текущим trusted Recovery ISO;
- создаётся временная UEFI-запись для `\EFI\BOOT\BOOTX64.EFI` с `efibootmgr -C`, после чего только `BootNext` указывает на неё; постоянный `BootOrder` не меняется;
- USB boot options несут `arch_manager_usb=1`, поэтому автономный мастер знает, что запущен с флешки, и при отмене автоматически перезагружает машину обратно в обычную систему;
- если автоматический BootNext недоступен, сама Recovery-флешка остаётся загрузочной и её можно выбрать через firmware Boot Menu.

## Граница безопасности

Подготовка среды не выполняет восстановление и не перезагружает систему. Реальное переключение `@` остаётся только внутри автономного Recovery engine.

Перед следующими изменениями:

1. сделать резервную копию;
2. не переносить произвольные shell-команды в GUI;
3. запускать полный pytest и Python/Bash syntax checks;
4. не запускать реальное восстановление из тестов.
Recovery 1.8.6 отображает время точек восстановления в Europe/Moscow (MSK, UTC+3) и сохраняет текущий `~/.config/ksmserverrc` при системном rollback, чтобы подтверждение выключения/перезагрузки Plasma не возвращалось к старому состоянию из snapshot.
Recovery 1.8.7 синхронизирует нумерацию точек с GUI во всех автономных режимах: локальный Recovery и USB Recovery автоматически используют тот же порядок 1..N после создания или удаления точек. Сохраняются исправления московского времени и Plasma ksmserverrc.
Recovery 1.8.8 исторически добавлял процентный progress-bar; начиная с Recovery 1.8.10 он удалён как лишний для быстрых этапов автономного восстановления.

Автономный engine умеет аварийно откатывать уже начатую замену `@`, проверяет неизменяемость выбранного snapshot и соответствие отдельного boot-раздела. USB-путь защищён fingerprint выбранного физического носителя, блокировкой системных mount/swap, безопасными временными файлами и cleanup фоновых процессов. Все изменяющие Recovery-действия дополнительно сериализованы root-owned `flock`, чтобы параллельные экземпляры Arch Manager не конфликтовали. Recovery ISO устанавливается атомарно, а hash профиля учитывает symlink targets. Русский TTY остаётся UTF-8/кириллическим; отдельный regression-тест запрещает русский транслит латиницей.

## Классификация системных предупреждений — 28.09.2026

Уточнена диагностика раздела «Система» по результатам проверки реального Arch-хоста:

- `bootctl status` теперь определяет фактически запущенный systemd-boot по `Current Boot Loader`, поэтому `Permission denied` при чтении защищённого ESP больше не превращается в ложное «systemd-boot не активен»;
- известная комбинация systemd 262 + TPM/NvPCR unit-ы + `No such file or directory` классифицируется как информационная регрессия, если критических failed unit-ов нет;
- `journalctl -b -p err` больше не оценивается по сырому числу строк: сообщения группируются по причинам;
- ACPI BIOS Error считается одной категорией предупреждения прошивки, повторяющиеся строки не увеличивают «серьёзность»;
- TDX not supported, известные NvPCR-сообщения, SMBus busy и неподдерживаемая возможность nl80211/Wi-Fi классифицируются отдельно как информационные/низкоприоритетные;
- Btrfs/I/O/NVMe critical, kernel panic, Oops/BUG и MCE остаются критическими;
- kernel taint `512` показывается как `W` (kernel warning), то есть след предупреждения, а не отдельная неисправность;
- при наличии только информационных заметок общий статус остаётся зелёным.

## Уточнение диагностики и интерфейса «Система» — 28.09.2026

После проверки на реальной загрузке systemd 262 уточнены классификация и отображение результатов:

- известная связка `systemd 262 + NvPCR + No such file or directory` определяется через `systemctl --version` (с fallback на pacman), поэтому четыре NvPCR unit-а и `degraded` больше не создают самостоятельное предупреждение системы;
- `bootctl status` используется по данным текущего загрузчика даже при закрытом для обычного пользователя ESP; Secure Boot и TPM показываются человекочитаемыми русскими формулировками;

### Recovery 1.8.15 — стабилизация Unicode TTY перед выводом интерфейса

### Recovery 1.8.16 — безопасная инициализация TTY без зависания загрузки

Версия 1.8.15 слишком агрессивно пыталась исправить кириллицу: перед запуском мастера выполнялись `udevadm settle`, повторные `setfont` и искусственные задержки во время перехода framebuffer → DRM/KMS, а затем похожая настройка повторялась из самого Recovery-движка. ### Recovery 1.8.17 — постоянный boot-log и защитный watchdog запуска

Recovery теперь ведёт ранний журнал запуска в `/run/arch-manager/recovery-boot.log` и после обнаружения системного Btrfs сохраняет его в `@snapshots/.arch-manager-recovery/boot/` (последняя копия — `last-boot.log`).

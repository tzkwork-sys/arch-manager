# Участие в разработке

Спасибо за интерес к Arch Manager! Ошибки, предложения, документация и Pull
Request приветствуются. Официальные изменения и выпуски принимает владелец проекта.
Отправка PR не гарантирует его включение в проект.

## Порядок работы

1. Для заметного изменения сначала откройте Issue и согласуйте направление.
2. Сделайте fork, создайте отдельную ветку и внесите небольшое тематическое изменение.
3. Добавьте тесты и обновите документацию, если поведение изменилось.
4. Запустите проверки и отправьте Pull Request с описанием цели и результата.
5. Дождитесь проверки владельцем; не объединяйте несвязанные изменения в один PR.

Нельзя включать чужой код, изображения или иные материалы без совместимой
лицензии и указания происхождения. Внося свой вклад, вы соглашаетесь на его
распространение под GPL-3.0-only, без передачи исключительных прав владельцу.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
QT_QPA_PLATFORM=offscreen python -m pytest -q
python -m compileall -q src tests main.py
git ls-files -z '*.sh' | xargs -0 -r -n1 bash -n
bash -n recovery/arch-manager-recovery
desktop-file-validate desktop/arch-manager-gui.desktop
git diff --check
```

Автоматические тесты не доказывают безопасность реального восстановления.
Системные операции проверяйте только в изолированной среде, на расходных дисках
или VM, с независимой резервной копией. В PR укажите, какие проверки были
реально выполнены, а какие нет.

## Границы безопасности

- GUI не должен работать от root, получать или сохранять пароль администратора.
- Не добавляйте произвольные shell-команды в привилегированный интерфейс.
- Аргументы должны проверяться повторно в системном компоненте.
- Не ослабляйте проверки дисков, snapshots, подписей, прав файлов и блокировок.
- Не отключайте авторизацию и не добавляйте широкие NOPASSWD-разрешения.
- Не завершайте pacman принудительно только из-за истечения тайм-аута.

## Принятие изменений

Исправления в официальный проект включаются после решения владельца.
CODEOWNERS лишь назначает рецензента; защита ветки и обязательные проверки
настраиваются отдельно на GitHub. Прямой доступ к записи сторонним авторам
для работы через fork/PR не нужен.

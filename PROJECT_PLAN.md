# Arch Manager — план перехода к полноценному GUI-приложению

Для аварийного восстановления используется одна минимальная Arch Manager Recovery environment: local one-shot boot уже использует её, а будущая USB-флешка будет записывать тот же образ. Это не полноценная Arch live system; после boot автоматически запускается мастер.

## 1. Цель проекта

Arch Manager должен стать полноценным графическим служебным приложением для Arch Linux: понятным обычному пользователю, но достаточно информативным для уверенного контроля системы.

Главный принцип: **пользователь работает не с Linux-командами, Btrfs, Snapper и терминологией системного администратора, а с понятными действиями и состояниями системы.**

Приложение должно помогать:

- видеть состояние системы на одном экране;
- безопасно устанавливать обновления;
- создавать точки восстановления;
- возвращать систему к выбранному состоянию;
- обслуживать систему и освобождать место;
- видеть проблемы и получать понятные рекомендации;
- подготовить аварийное восстановление, если система перестала загружаться.

## 2. Терминология интерфейса

### Не использовать в пользовательском интерфейсе

По возможности не показывать обычному пользователю технические термины без необходимости:

- `snapshot`;
- `subvolume` / «подтом»;
- `Btrfs @`;
- `Snapper`;
- `pacman`;
- `yay`;
- `systemd unit`;
- `journalctl`;
- `UKI`, `initramfs` и другие внутренние детали.

Они допустимы только в расширенной технической информации, журнале или режиме для опытного пользователя.

### Основной термин для snapshot

В GUI использовать:

**Точка восстановления**

Короткое объяснение при необходимости:

> Точка восстановления — сохранённое состояние системы, к которому можно вернуться, если обновление или изменение вызовет проблемы.

Термин **«Снимок системы»** можно использовать в поясняющем тексте, но не как главный элемент навигации.

Внутренние имена старого кода (`snapshot_*`) на первых этапах можно не менять: пользователь их не видит. Они будут переименовываться по мере переноса логики в новое ядро.

## 3. Принципы интерфейса

### 3.1. Понятность важнее технической точности формулировок

Каждый экран должен отвечать на три вопроса:

1. Что сейчас происходит с системой?
2. Нужно ли пользователю что-то делать?
3. Как выполнить нужное действие безопасно?

### 3.2. Минимум переходов между экранами

С конкретной точки восстановления пользователь должен иметь возможность выполнить максимум связанных действий прямо там:

- посмотреть дату и время;
- увидеть название/описание;
- увидеть занимаемое место;
- увидеть причину создания;
- отметить как важную;
- переименовать;
- удалить;
- начать восстановление;
- открыть дополнительные сведения.

При этом редкие и опасные действия не должны визуально конкурировать с основными.

### 3.3. Прогрессивное раскрытие информации

По умолчанию показывать только понятную и полезную информацию.

Дополнительные сведения открывать по кнопке вроде:

**Подробнее** / **Техническая информация**

Например, обычный пользователь видит:

- «Создана перед обновлением системы»;
- «21 сентября 2026, 11:42»;
- «Занимает дополнительно 684 МБ»;
- «Важная точка».

А в технических сведениях можно показать Btrfs/Snapper ID, путь, подтом, служебные поля и другие детали.

### 3.4. Не перегружать главный экран

Главный экран должен показывать итоговое состояние, а не поток диагностической информации.

Пример карточек:

- **Система:** всё в порядке / требуется внимание;
- **Обновления:** 12 доступно;
- **Точки восстановления:** 7;
- **Последняя точка:** сегодня, 11:42;
- **Место на диске:** 63 ГБ свободно;
- **Обслуживание:** можно освободить 1,4 ГБ.

### 3.5. Опасные действия всегда объяснять

Перед удалением точки восстановления, восстановлением системы или очисткой важных данных показывать:

- что именно будет сделано;
- что сохранится;
- что может измениться;
- есть ли возможность отмены;
- какую защитную копию Arch Manager создаст автоматически.

## 4. Отображение размера точки восстановления

Размер должен показываться обязательно, но формулировка должна быть понятной и честной.

Btrfs использует совместно разделяемые блоки, поэтому «полный размер папки» может вводить в заблуждение. В интерфейсе основной показатель лучше формулировать как:

**Занимает дополнительно: 684 МБ**

или

**Дополнительное место: 684 МБ**

Это ближе к фактическому уникальному/эксклюзивному объёму данных точки восстановления.

Если точный расчёт временно недоступен:

**Размер: рассчитывается…**

Технический способ расчёта не показывать без открытия дополнительных сведений.

## 5. Рекомендуемый стек

### Основной GUI

- **Python 3**
- **PySide6 / Qt 6**
- **Qt Widgets** для первой полноценной GUI-версии

Причины:

- хорошо интегрируется с KDE Plasma;
- нативный внешний вид с Breeze;
- нормальная работа под Wayland;
- таблицы, карточки, диалоги, progress bar и мастера без web-обвязки;
- Python удобен для вызова и постепенной замены существующей Bash-логики.

### Повышенные права

- GUI всегда работает от обычного пользователя;
- привилегированные действия выполняются отдельным helper-компонентом;
- запрос прав — через **Polkit** и стандартное окно KDE.

### Аварийное восстановление

`arch-recovery.sh` оставить автономным Bash-компонентом как минимум на длительный переходный период.

Причина: аварийная среда не должна зависеть от Plasma, PySide6 и полноценного графического окружения.

## 7. Предлагаемая структура главного окна

Левая навигация (актуальная компактная схема):

1. **Обзор**
2. **Обновления**

Журнал не занимает отдельный пункт бокового меню: он относится к служебным настройкам и истории работы приложения.

## 8. Экран «Обзор»

Это стартовая страница после запуска приложения.

Она должна показывать только самое важное:

### Верхняя часть

- общий статус: **Всё в порядке** / **Требуется внимание**;
- дата последней проверки;
- кнопка **Проверить сейчас**.

### Карточки

**Обновления**
- количество;
- есть ли важные системные обновления;
- кнопка **Посмотреть** или **Обновить**.

**Точки восстановления**
- количество;
- последняя дата;
- занятое дополнительное место;
- кнопка **Создать точку**.

**Обслуживание**
- сколько места можно безопасно освободить;
- наличие старых пакетов, кэша, журналов;
- кнопка **Проверить**.

**Система**
- свободное место;
- наличие системных ошибок;
- состояние загрузки/восстановления простыми словами.

Главная страница не должна показывать список пакетов, строки журнала или технические идентификаторы.

---

## 9. Экран «Точки восстановления»

Это один из центральных экранов приложения.

### Список

Для каждой точки показывать:

- понятное название;
- дату и время;
- причину создания;
- дополнительный занимаемый объём;
- статус «важная»;
- при необходимости значок автоматической/ручной точки.

### Действия с выбранной точкой

На том же экране:

- **Восстановить систему**;
- **Переименовать**;
- **Сделать важной / снять отметку**;
- **Удалить**;
- **Подробнее**.

Кнопка восстановления должна быть заметной, но визуально отделённой от удаления.

### Создание

Кнопка:

**Создать точку восстановления**

Дополнительно можно предложить необязательное название:

> Например: «Перед установкой драйвера»

## 10. Экран «Обновления»

Пользовательский уровень:

- сколько обновлений найдено;
- список программ/компонентов;
- текущая и новая версии;
- источник можно показывать как **Системный** и **Дополнительный**, а не обязательно `pacman` и `AUR` в основном режиме;
- кнопка **Обновить всё**.

Перед обновлением, если функция включена, Arch Manager автоматически создаёт точку восстановления.

В процессе показывать этапы человеческим языком:

1. Подготовка;
2. Создание точки восстановления;
3. Загрузка обновлений;
4. Установка;
5. Проверка результата.

Полный вывод терминала скрывать под **Подробности**.

---

## 11. Экран «Обслуживание»

Вместо набора технических команд показывать понятные категории:

- **Кэш обновлений**;
- **Ненужные пакеты**;
- **Системный журнал**;
- **Оставшиеся файлы настроек после обновлений**;
- дополнительные безопасные категории в будущем.

Сначала Arch Manager делает анализ и показывает:

**Можно освободить примерно 1,4 ГБ**

Затем пользователь выбирает категории и запускает очистку.

---

## 12. Экран «Восстановление»

Раздел должен объединять:

- восстановление из точки восстановления;
- состояние аварийной среды;
- подготовку локального восстановления;
- создание аварийного USB-носителя;
- проверку результата последнего восстановления;
- безопасное удаление старой резервной копии корневой системы после проверки.

Технические понятия `@.broken`, root subvolume и т.п. в основном интерфейсе переводятся в понятные названия, например:

**Резервная копия системы до последнего восстановления**

В технических подробностях можно показать исходное имя `@.broken-...`.

## 13. Архитектура приложения

```text
GUI (PySide6 / Qt)
        │
        ├── core: безопасные операции без root
        │
        ├── privileged helper + Polkit
        │       ├── обновление системы
        │       ├── системная очистка
        │       ├── операции Btrfs
        │       └── подготовка восстановления
        │
        └── recovery subsystem
                └── arch-recovery.sh / автономная среда
```

GUI не должен содержать длинную системную Bash-логику внутри обработчиков кнопок.

Каждая функция должна иметь отдельный backend-метод с понятным результатом, который GUI отображает человеку.

## 14. Формат результатов от ядра к GUI

Вместо анализа текста команд самим интерфейсом ядро постепенно должно возвращать структурированные данные.

Условный пример:

```python
{
    "ok": True,
    "title": "Точка восстановления создана",
    "restore_point_id": 143,
    "created_at": "2026-09-21T12:30:00",
    "reason": "Перед обновлением системы",
    "exclusive_size_bytes": 717225984,
}
```

GUI сам решает, как это красиво показать.

Это позволит позднее менять внешний вид без переписывания системной логики.

## 15. Перенос существующего Bash-кода

Переносить **по функциональным блокам**, а не переписывать весь `arch-manager.sh` сразу.

### Остаётся временно в legacy

В текущей версии уже есть рабочая логика:

- создание и управление точками восстановления;
- расчёт дополнительного размера;
- защита важных точек;
- политика автоматического создания;
- восстановление;
- подготовка Recovery;
- создание аварийной флешки;
- проверка последнего восстановления;
- официальные обновления;
- AUR-обновления;
- обслуживание системы;
- проверка состояния системы.

Эта логика является референсом при переносе.

### Правило удаления legacy-кода

Функция из старой версии удаляется только когда:

1. её backend перенесён;
2. GUI использует новый backend;
3. проведён реальный тест;
4. проверен сценарий ошибки;
5. старый код больше нигде не вызывается.

**Статус: реализовано.**

### Этап 2 — «Обзор» и информация о системе

Перенести безопасные read-only функции:

- информация о системе;

Это даст полезное GUI-приложение без root-операций.

**Статус: реализовано в 0.2.0-stage2.**

### Этап 3 — точки восстановления: просмотр

- новый backend `restore_points.py`;
- получение списка;

- расчёт дополнительного размера;

### Этап 4 — точки восстановления: действия

- создание;
- переименование;
- важная/обычная;
- удаление;
- политика автоматического создания;
- подтверждения опасных операций;
- Polkit/helper там, где он нужен.

**Статус: реализовано в 0.4.4-stage4.**

### Этап 5 — обновления

- проверка официальных обновлений;
- проверка дополнительных/AUR-обновлений;
- единый список;
- создание точки перед обновлением;
- установка;
- progress UI;
- скрываемый технический журнал.

**Статус: реализовано в 0.5.2-stage5.** Проверены единый список официальных/AUR-обновлений, защитная точка, интерактивная установка, итоговый отчёт, проверка перезагрузки и локальный журнал.

### Этап 6 — обслуживание

- анализ;
- понятные категории очистки;
- оценка освобождаемого места;
- выбор действий;
- выполнение через helper;
- итоговый отчёт.

**Статус: реализовано в 0.6.1-stage6.** Добавлены выборочная очистка кэша пакетов, ненужных зависимостей, архивных журналов, кэша миниатюр и корзины; `.pacnew/.pacsave/.pacorig` остаются только для ручной проверки.

### Этап 7 — восстановление

- выбор точки;
- понятный мастер восстановления;
- подготовка локальной Recovery-среды;
- проверка готовности;
- перезагрузка в Recovery;
- состояние последнего восстановления;
- удаление старой резервной системы только после успешной проверки.

`arch-recovery.sh` на этом этапе остаётся автономным и используется как проверенное аварийное ядро.

**Статус: Stages 7A–7B.1 реализованы в текущей рабочей ветке; полный этап не завершён.** Добавлены read-only backend, общий Recovery environment, ограниченный Polkit-helper, minimal project-owned ArchISO profile, versioned SHA-256 validation, быстрый fingerprint для повторных входов на страницу и однократное направление следующей загрузки в Recovery. Выбор точки выполняется уже в автономном Recovery UI; видимые номера идут подряд `1…N`, а внутренние Snapper ID не меняются. Само выполнение Recovery engine остаётся автономным.

- защита от выбора системного диска;
- понятные предупреждения;
- создание носителя;

### Этап 9 — упаковка приложения

- PKGBUILD;
- установка в системные каталоги;
- `.desktop`;
- SVG-иконка;

### Recovery 1.8.17 — постоянный boot-log и защитный watchdog запуска

Recovery теперь ведёт ранний журнал запуска в `/run/arch-manager/recovery-boot.log` и после обнаружения системного Btrfs сохраняет его в `@snapshots/.arch-manager-recovery/boot/` (последняя копия — `last-boot.log`). В журнал пишутся стадии: старт engine, параметры режима, UTF-8 TTY, поиск системного раздела, mount верхнего уровня Btrfs и построение списка точек. При зависании старта отдельный `arch-manager-recovery-watchdog.service` ждёт 60 секунд. Если мастер не дошёл до готового списка точек, watchdog дописывает `systemctl`, journal, `lsblk`, `findmnt` и хвост `dmesg`, сохраняет лог и прекращает бесконечное ожидание: локальный Recovery возвращается обычной перезагрузкой в Arch Linux, USB/manual Recovery выключает компьютер, чтобы не получить цикл загрузки с флешки. Watchdog отключается до выбора точки и не участвует в самой операции восстановления. Одновременно сохранено исправление 1.8.16: нет `udevadm settle`, циклов `setfont` и искусственных задержек во время KMS/TTY handover; шрифт `UniCyr_8x16` загружает `systemd-vconsole-setup`. Версия engine — 1.8.17, `iso_version` — 8, поэтому локальный Recovery ISO должен быть пересобран, а USB Recovery — один раз перезаписан.

### Recovery 1.8.18 — безопасный порядок запуска TTY + boot-log/watchdog
Исправлена регрессия 1.8.17: в обычном local/USB режиме поиск системного Btrfs выполняется до позднего переключения tty1 в UTF-8, а его ранний пользовательский вывод подавляется. После успешного поиска и монтирования tty1 один раз переводится в UTF-8, экран очищается и только затем рисуется русскоязычный интерфейс. Это сохраняет защиту от KMS/TTY-зависания и одновременно не возвращает русский транслит. Для ручного режима консоль готовится отдельной обёрткой перед возможными интерактивными вопросами. Постоянный boot-log и 60-секундный watchdog сохранены. Версия Recovery 1.8.18, iso_version=9.



### Recovery 1.8.21: resilient Cyrillic console font fallback

Recovery no longer aborts when a single hard-coded console font name cannot be loaded. Immediately before the first menu draw it resolves an installed Cyrillic-capable PSF file from a deterministic kbd fallback list (LatArCyrHeb/LatGrkCyr/Cyr/UniCyr), attempts a font load, enables Linux-console UTF-8 mode, and continues even if the kernel rejects all font changes. Built-in menu labels remain English/ASCII, while UTF-8 restore-point descriptions are preserved unchanged. This removes the fatal `Could not load the Recovery console font` regression while retaining a single menu draw. Engine version is 1.8.21 and `iso_version` is 12.

### Recovery 1.8.22: single stable menu and correct Cyrillic descriptions

Recovery now decodes Snapper XML numeric character references into UTF-8 bytes without depending on the process locale, including legacy double-escaped `&amp;#xNNNN;` descriptions. The recovery UI takes a single-instance lock, and systemd no longer resets or hangs up tty1 around the wizard; the engine itself performs the only screen clear immediately before the final menu draw. `iso_version` is 13 so the cached Recovery ISO is forced to rebuild.

### Recovery 1.9.0: one visible draw and full Cyrillic descriptions

- Recovery UI is prepared off-screen on dedicated `/dev/tty2` and activated exactly once after the table is complete.
- `arch-manager-recovery.service` uses `Type=idle`; tty2 getty is masked/conflicted to prevent later console takeover.
- Known legacy `Arch Manager: pered obnov...` automatic descriptions are normalized for display to Cyrillic without modifying snapshot metadata.
- Description text is no longer truncated with ellipsis. Compact table widths fit the standard automatic description in 80 columns; longer text is wrapped on continuation lines.
- Recovery version is 1.9.0 and Archiso profile version is 14 to invalidate the previous cached ISO.

### Recovery 1.9.0: clean console-menu rewrite

The accumulated hidden-tty2/chvt startup path was removed. Recovery now has one systemd owner for `/dev/tty1`, one console setup pass, one screen clear and one menu render. There is no hidden VT switch and no second copy of the table. Restore-point descriptions keep full UTF-8 text; the known legacy `pered obnov...` automatic description is repaired only at display time. `iso_version=15` invalidates the previous cached ISO.
